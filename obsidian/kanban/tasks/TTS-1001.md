## 🟢 TTS-1001: Prefix command ?say ให้บอทพูดใน voice channel ด้วยเสียง Liino

Status: Review
Priority: High
Ref: 📝・liino-notes (โพสต์ QTTTS-SAY-CMD)

### Summary
สร้าง prefix command `?say <ข้อความ> [--mood ...]` (text command ไม่ใช่ Discord slash command เพื่อเลี่ยงการชนกับ bot อื่น) ให้บอทเข้า voice channel ที่ผู้สั่งอยู่ สร้างเสียงด้วย qwen3-tts (voice = Liino) เล่นข้อความ แล้วจัดการการอยู่/ออกจากห้องอย่างเหมาะสม

### Context
- โปรเจกต์ qwen3-tts พร้อมแล้ว: voice clone Liino, daemon พร้อม FIFO queue + cache + mood presets 11 แบบ (`--mood` ใน `qwen_clone_tts.py`)
- เคยเล่นเสียงใน voice channel ได้แล้ว (Liino_Intro)
- Consumer หลักคือ Hermes agent ที่ shell ออกไปเรียก `qwen_clone_tts.py --stdin <input.txt> <output.wav>` — ดู `README_HERMES.md`

### Scope
- Prefix command `?say` พร้อม option: ข้อความ (จำกัดความยาว ≤ MAX_CHARS), `--mood` (mood preset)
- เรียก TTS ผ่าน daemon fast path (`/tmp/qwen_tts_daemon.sock`) ถ้า daemon ไม่ขึ้นให้ fallback หรือแจ้ง error ชัดเจน
- บอท join voice channel ของผู้ใช้, เล่นไฟล์เสียง, จบแล้วตัดสินใจอยู่/ออก (idle timeout หรือออกทันที — ระบุใน plan)
- จัดคิวเมื่อมีคำสั่งซ้อนกัน (ต่อยอด FIFO queue ของ daemon)

### Acceptance Criteria
- `?say สวัสดี` ใน VC → บอทเข้าห้อง พูด "สวัสดี" ด้วยเสียง Liino
- `?say <ข้อความ> --mood excited` → เสียงมีอารมณ์ตาม preset
- คำสั่งซ้อนกันเล่นเรียงคิว ไม่ทับกัน
- ข้อความเกิน MAX_CHARS ถูกปฏิเสธพร้อมข้อความ error ที่อ่านเข้าใจ
- daemon ล่ม → แจ้ง error ชัดเจน ไม่ค้าง
- Validation ผ่านการรันจริงทุกข้อ (ไม่มี automated test suite)

### Validation
- รันจริงใน Discord: `?say` ปกติ, `--mood`, ข้อความยาวเกินลิมิต, กรณี daemon ล่ม
- ตรวจ stdout contract `OK <path>` / `ERROR: ...` ของ `qwen_clone_tts.py`

### Open Questions
(ทั้งหมด resolved — decisions อยู่ใน Context/Scope)

### Decisions
- Implement ในโปรเจกต์ qwen3-tts เอง (เพิ่ม Discord bot gateway เข้ามาในโปรเจกต์)
- บอท idle รอใน VC หลังพูดจบ (default 60 วินาที ปรับได้) ค่อยออกเมื่อไม่มีคำสั่งใหม่

### Implementation Plan

- Context to verify:
  - README.md (Goal/Tech Stack) ระบุชัดว่าโปรเจกต์นี้ "ไม่มี Discord bot" — ticket นี้ขัดกับ behavior เดิมตรง ๆ ผู้ใช้ (Liino) อนุมัติเป็น **exception เฉพาะ ticket นี้** แล้ว (ยืนยันซ้ำในคำสั่ง plan นี้) — ต้องอัปเดต README.md (Goal/Tech Stack/Features/CLI Reference) ตอน implement ไม่ใช่ตอน plan
  - `qwen_clone_tts.py` เป็น source of truth ของ `MAX_CHARS` (300), `MOOD_PRESETS`, `resolve_instruct()`, และ `_try_daemon()` (fast path ผ่าน `/tmp/qwen_tts_daemon.sock`) — bot ต้อง import/reuse ของเดิม ห้าม duplicate ค่า/logic
  - `tts_daemon.py` มี FIFO queue ของตัวเองอยู่แล้วสำหรับ "การสร้างเสียง" (text→wav) แต่ไม่มี concept ของ "คิวการเล่นเสียงในห้อง VC" — ต้องสร้างคิวเล่นเสียงแยกต่างหากฝั่งบอท (per-guild) เพื่อให้ AC "คำสั่งซ้อนกันเล่นเรียงคิว ไม่ทับกัน" เป็นจริงตอนเล่นไฟล์ ไม่ใช่แค่ตอน generate
  - README_HERMES.md § Discord voice_fx เป็นของ**คนละโปรเจกต์** (Hermes agent's Discord adapter) — ไม่เกี่ยวกับ bot ที่ ticket นี้จะสร้างใน repo นี้ ใช้เป็นแค่ reference ว่าเคยเล่นเสียงใน VC ได้มาก่อน (Liino_Intro)
  - Repo convention: ไม่มี `src/` layout (script เดี่ยวที่ root), config ผ่าน env var ล้วน (ไม่มี config file), CLI/script report ผล stdout/stderr ธรรมดา, subprocess เรียก ffmpeg ต้องเป็น list arg ห้าม `shell=True`

- Planned changes:
  - สร้างสคริปต์ใหม่ `discord_say_bot.py` ที่ root ของ repo (entry point ใหม่ ผู้ใช้เรียกตรง `.venv/bin/python discord_say_bot.py`) ใช้ `discord.py` (gateway + voice) เป็น Discord client
  - Prefix command `?say <ข้อความ> [--mood <preset>]`:
    - ต้องเปิด privileged **Message Content Intent** ใน Discord Developer Portal (นอกเหนือ code) เพื่อให้อ่านข้อความ prefix command ได้ — บันทึกเป็น deployment prerequisite
    - Parse `--mood` ออกจากข้อความเอง (prefix command ธรรมดา ไม่มี option parser ของ slash command) แล้วโยนที่เหลือเป็น `text`
    - Validate ความยาวด้วย `qwen_clone_tts.MAX_CHARS` ก่อนทำอะไรอื่น — เกินลิมิตให้ reply error ที่อ่านเข้าใจทันที ไม่เข้าคิว
    - ถ้าผู้สั่งไม่ได้อยู่ใน voice channel ใด ๆ → reply error ชัดเจน ไม่ join ห้องมั่ว
  - เรียก TTS ผ่าน daemon fast path โดย import `qwen_clone_tts._try_daemon()` (หรือ equivalent เรียก socket protocol เดิมตรง ๆ) รันใน `asyncio.to_thread(...)` เสมอ (ห้ามเรียก sync ตรงใน event loop — จะบล็อก heartbeat ของ discord.py)
  - **Decision (daemon ล่ม)**: ถ้า `_try_daemon()` คืน False (socket ไม่มี/ตอบ error) ให้ bot **รายงาน error ชัดเจนทันที ไม่ fallback ไปโหลดโมเดลเอง** ภายใน bot process — ตีความ AC "daemon ล่ม → แจ้ง error ชัดเจน ไม่ค้าง" ว่าห้ามให้ bot ไปเดิน slow path (~3-10s+ โหลดโมเดล ~6.7GB) ที่ทำให้ผู้ใช้รู้สึกค้าง ซึ่งต่างจาก behavior ปกติของ `qwen_clone_tts.py` CLI ที่ fallback อัตโนมัติ — เป็น deviation ที่ตั้งใจ เฉพาะ path ของบอทเท่านั้น (CLI เดิมไม่แตะ)
  - Playback queue ต่อ guild (`dict[guild_id, asyncio.Queue]`) — เพิ่ม job (wav path + text meta) เข้าคิวเมื่อ generate เสร็จ, worker task ต่อ guild เล่นทีละไฟล์ผ่าน `discord.FFmpegPCMAudio` + รอ `after` callback ก่อนเล่นตัวถัดไป (กัน AC "เล่นเรียงคิว ไม่ทับกัน")
  - Idle-leave: หลังคิวว่างและเล่นจบ เริ่ม countdown `VC_IDLE_TIMEOUT_S` (default 60, override ผ่าน env var) — ถ้ามีงานใหม่เข้าคิวก่อนครบเวลาให้ cancel countdown, ถ้าไม่มีให้ `voice_client.disconnect()`
  - เพิ่ม env var ใหม่ (อ่านจาก `.env`/process env เท่านั้น ตาม convention เดิม ไม่มี config file):
    - `DISCORD_BOT_TOKEN` (secret, required, ห้าม hardcode)
    - `DISCORD_COMMAND_PREFIX` (default `?`)
    - `VC_IDLE_TIMEOUT_S` (default `60`)
  - เพิ่ม dependency ใหม่ใน `requirements.txt`: `discord.py` (พร้อม voice extra) + `PyNaCl` (จำเป็นสำหรับ voice encryption ของ discord.py)
  - อัปเดต `README.md`: แก้ข้อความ Goal/Tech Stack ที่ระบุ "ไม่มี Discord bot", เพิ่มตาราง env var ใหม่, เพิ่มวิธีรัน/ตั้งค่าบอท (ตาม post-implementation gate ของ kanban-flow ข้อ 2)
  - Scope ที่ตั้งใจ "ไม่ทำ" ใน ticket นี้ (เพื่อไม่ scope-creep): ไม่ทำ launchd service สำหรับบอท (ticket ไม่ได้ระบุ), ไม่เปิด long-text auto-chunk (`chunk_text`) ฝั่งบอท — ใช้ MAX_CHARS reject ตรง ๆ ตาม AC

- Risks / decisions:
  - **README conflict (approved exception)**: README.md ปัจจุบันระบุ "ไม่มี Discord bot" — ผู้ใช้อนุมัติ exception เฉพาะ ticket นี้แล้ว ต้องอัปเดต README ให้ตรงความจริงตอน implement มิเช่นนั้นเอกสารจะขัดกับโค้ด
  - **Deployment prerequisite นอกโค้ด**: ต้องเปิด Message Content Intent ใน Discord Developer Portal + บอทต้องมีสิทธิ์ Connect/Speak ในห้อง — ถ้าไม่เปิดจะดูเหมือนบอท "ไม่ตอบสนอง" โดยไม่มี error ชัดเจนในโค้ด
  - **Secret handling**: `DISCORD_BOT_TOKEN` ต้องมาจาก `.env`/env var เท่านั้น (`.env` ถูก gitignore ไว้แล้ว) ห้าม hardcode หรือ commit
  - **Event loop blocking**: ต้องเรียก TTS generation ผ่าน `asyncio.to_thread`/executor เสมอ ไม่เรียก sync ตรงใน coroutine — ไม่งั้น heartbeat ของ discord.py จะเด้ง/disconnect ตอน generate นาน
  - **Deviation จาก CLI เดิม**: บอทจะไม่ fallback ไปโหลดโมเดลเองเมื่อ daemon ล่ม (ต่างจาก `qwen_clone_tts.py` ปกติ) — ตัดสินใจไว้ในแผนนี้แล้วเพื่อไม่ให้เดาเองตอน implement แต่เป็นจุดที่ reviewer ควรตรวจซ้ำตอน code review
  - **New dependency footprint**: `discord.py`/`PyNaCl` เป็น dependency ใหม่ที่ไม่เคยมีในโปรเจกต์นี้ — ต้อง `pip install -r requirements.txt` ใหม่หลัง merge
  - **Playback queue เป็นของใหม่ทั้งหมด**: ไม่มี pattern เดิมให้ reuse ในโปรเจกต์ (queue เดิมของ `tts_daemon.py` คือคิว generate ไม่ใช่คิวเล่นเสียง) — regression risk หลักของ ticket นี้ ควรผ่าน `code-review` (และพิจารณา `security-review` เพราะมีจุดเรียก subprocess/ffmpeg ผ่าน `discord.FFmpegPCMAudio`) ก่อนเข้า done
  - ไม่มี automated test suite ในโปรเจกต์นี้ — คง manual validation เป็นหลักตาม convention เดิม ไม่เพิ่ม `pytest` เว้นแต่พบ pure logic ที่คุ้มค่าเขียน unit test (เช่น `--mood` text parser) ซึ่งจะตัดสินใจอีกครั้งตอน implement
