## 🟢 TTS-1003: ?say เปลี่ยนลิมิตเป็นต่อบรรทัด + จำนวนบรรทัดไม่จำกัด

Status: Backlog
Priority: Medium
Ref: idea จาก Wyitz (2026-08-30, thread นี้)

### Summary
ปรับ `?say` (TTS-1002) จากการเช็คลิมิตแบบ "รวมทุกบรรทัด ≤ MAX_CHARS" เป็น "ต่อบรรทัด ≤ MAX_CHARS" และยกเลิกข้อจำกัดจำนวนบรรทัด — ผู้ใช้สร้าง array (ประโยค) ได้ไม่จำกัด

### Context
- TTS-1002 (DONE) เช็ค total chars ทุกบรรทัดรวมกัน ≤ MAX_CHARS (300) — บังคับให้ข้อความยาวหลายบรรทัดถูก reject ทั้ง batch แม้แต่ละบรรทัดสั้น
- `MAX_CHARS` (300) เป็น hard limit **ต่อ request หนึ่งครั้งของ daemon** (`tts_daemon.py` reject ก่อนเข้าคิว) — แปลว่า per-line ≤ 300 สอดคล้อง daemon โดยตรง; total-limit ของบอทเป็นกฎที่เข้มกว่าจำเป็น
- Generate ทีละบรรทัดผ่าน daemon FIFO queue อยู่แล้ว — เพิ่มบรรทัดไม่กระทบ protocol; ผลข้างเคียงคือ generation time ยาวขึ้นตามจำนวนบรรทัด (queue ทำงานลำดับเดิม)
- Atomic batch (TTS-1002): บรรทัดไหน fail → ลบ wav ทั้ง batch ไม่เล่นเลย — ยังใช้ได้กับบรรทัดเยอะ แต่ควรพิจารณา UX ตอน fail งานยาว

### Scope
- ลบ total-char check — เช็ค **per-line** ≤ MAX_CHARS (300) หลังตัด emoji/trim แทน; บรรทัดไหนเกิน → reply error ระบุบรรทัดที่ N เกิน ไม่เข้าคิวทั้ง batch
- ไม่จำกัดจำนวนบรรทัด (ผู้ใช้ยืนยัน 2026-08-30: ไม่ใส่ SAY_MAX_LINES — ใช้ส่วนตัว คุมเอง)
- คง atomic batch เดิม (ผู้ใช้ยืนยัน 2026-08-30): บรรทัดไหน fail → ลบ wav ทั้ง batch ไม่เล่นเลย reply error ชัดเจน
- อัปเดต error message/README/help text ให้ตรง ("เกิน 300 ตัวอักษรต่อบรรทัด")
- อัปเดต unit test ใน `test_say_moods.py` ให้ครอบ per-line validation ใหม่

### Acceptance Criteria
- `?say` 5-10 บรรทัด แต่ละบรรทัด ≤ 300 → ผ่าน เล่นเรียงครบทุกบรรทัด
- รวมทุกบรรทัดเกิน 300 แต่ต่อบรรทัดไม่เกิน → **ผ่าน** (พฤติกรรมใหม่ ต่างจาก TTS-1002)
- บรรทัดใดบรรทัดหนึ่ง > 300 → reject ทั้ง batch พร้อมระบุเลขบรรทัด
- daemon queue รับงานเรียงลำดับถูกต้องเมื่อบรรทัดเยอะ
- unit test อัปเดตผ่านทั้งหมด

### Validation
- unit test: per-line check, บรรทัดเกิน → error message ระบุบรรทัด
- รันจริง: หลายบรรทัดรวมเกิน 300 → ผ่าน; บรรทัดเดียวยาว 301 → error ระบุบรรทัด
- regression: `?say` ธรรมดา 1 บรรทัด ยังทำงานเหมือนเดิม
